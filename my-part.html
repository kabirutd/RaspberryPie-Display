I develop the reports, so I’ll own the report pages, data-refresh settings, display refresh mechanism, and rotation. IT will handle the Pi, TV, network, startup, and any administrator-only settings.

Before I take over

  1. I’ll provide the exact report links and the pages and filters I want on the TV.
  2. I’ll grant the agreed display identity access where I have permission and ask an administrator for anything else.
  3. I’ll get access to the player settings or Pi scripts, plus the startup and recovery instructions.
  4. I’ll test my refresh configuration with IT and keep the support contacts and known sign-in limits in the handoff notes.

I’ll confirm which account is approved for the shared screen rather than treating my own work account as the default.

First: how do I get into the black box?

The Raspberry Pi is a small computer inside the box. The TV is its screen. The Pi runs the browser that opens Power BI.

I need an access handoff before I can own refresh. A powered-on box showing a report isn’t enough. IT needs to show me how to reach its desktop or player settings, which account to use, and where the configuration lives.

What I’ll ask IT first

“Is this running Raspberry Pi OS with Chromium, or a managed signage player? Please show me how to access the actual session displayed on the TV, open its settings or terminal, and change the refresh interval. I’ll need the Pi’s device name/address, an approved login, and the startup/recovery steps. Can we do the first change together?”

If it’s a managed signage appliance, I’ll use that product’s dashboard and refresh settings. The Linux scripts below may not apply. I won’t replace its software just to follow this example.

Option A: work directly at the TV

  1. I’ll connect a USB keyboard and mouse to the Pi’s USB ports, not the TV’s USB ports.
  2. IT will show me the approved way to pause the kiosk and reach the desktop. Alt+F4 can close Chromium, but a kiosk launcher may immediately reopen it unless paused first.
  3. On the Pi desktop, I’ll open the Terminal application from its menu.
  4. I’ll run hostname and whoami and compare the output with the device/account IT handed over.
  5. I’ll create or edit the script in this terminal. It is running on the Pi, even though I’m looking at the TV.

Option B: use my work computer

The simplest remote option for the first setup is IT-approved screen sharing into the same desktop session shown on the TV. I’ll open Terminal inside that shared desktop. A separate remote desktop session may not control the browser on the TV.

SSH is another option for editing files. IT must enable it and supply the actual username and hostname/IP. In Windows PowerShell, the connection command has this form; the names below are placeholders:

ssh PI_USERNAME@PI_HOSTNAME_OR_IP

After login, I’ll run hostname and whoami to check the machine and user. Subsequent Linux commands run on the Pi, not Windows. The scripts use $HOME, so I need the same local user as the kiosk desktop.

SSH is not the TV desktop. I can edit the files through SSH, but I won’t assume that launching Chromium or wtype from that shell controls the TV. For this example, the graphical scripts start through the Pi’s desktop autostart. I’ll test them in the TV desktop session or use a coordinated reboot.

Raspberry Pi’s remote-access documentation describes SSH and screen-sharing options. IT will choose the method allowed on our network.

My workflow using screen sharing

  1. I’ll connect to the company network or VPN and open IT’s approved screen-sharing tool.
  2. I’ll select the warehouse Pi and confirm that the session matches what’s on the TV.
  3. I’ll open Terminal in that shared desktop, pause the example automation, and edit the interval:
    touch "$HOME/warehouse-maintenance"
nano "$HOME/bin/warehouse-refresh.sh"
  4. For the single-report example, I’ll set REFRESH_SECONDS=300 for five minutes. I’ll save with Ctrl+O, Enter, and exit with Ctrl+X.
  5. I’ll remove the maintenance file and use the agreed helper restart or reboot procedure. For the reference setup, if I have reboot permission:
    rm -f "$HOME/warehouse-maintenance"
sudo reboot
    The remote session disconnects during reboot; I’ll reconnect after the Pi is back.
  6. I’ll watch the report reload and confirm it keeps the right page, filters, and full-screen display.

My workflow using SSH

In Windows PowerShell on my laptop, I’ll connect using the details IT supplied. These are placeholders:

ssh PI_USERNAME@PI_HOSTNAME_OR_IP

After connecting, I’ll confirm the machine and account:

hostname
whoami

I can then use the same pause/edit/save steps above in the remote shell. For logs, I can run:

tail -n 60 "$HOME/warehouse-refresh.log"

I won’t start an extra copy of the helper or Chromium from SSH. The example scripts start in the Pi’s desktop session through autostart. I’ll apply changes using the agreed restart method and use screen sharing to check the browser.

My laptop isn’t the refresh engine. Once configured, the Pi runs refresh automatically. I can close the remote session, disconnect from VPN, or shut down my laptop without stopping it. That assumes the helper is started independently through desktop autostart, rather than left running inside my SSH session.

The commands in this section apply to the example scripts, not every signage player. For a managed player, I’ll use its dashboard and documented restart controls.

What actually refreshes the screen?

For the Chromium example, warehouse-refresh.sh is a small file saved on the Pi. Once running, it waits for the configured interval and sends Ctrl+R to the focused browser. That is the same browser reload I could trigger with the Pi’s keyboard. It doesn’t run ingestion or a Direct Lake model update.

These HTML docs don’t install anything on the Pi. Opening this website or copying files to my Windows folder doesn’t start refresh on the warehouse display.

My first setup: one report, five-minute reload

  1. I’ll first confirm with IT that this is the Raspberry Pi OS / Wayland / labwc / Chromium setup used in the technical example. If it isn’t, we’ll use the installed player’s instructions instead.
  2. In the Pi desktop terminal, I’ll check for an existing helper before creating another:
    ls -l "$HOME/bin/warehouse-refresh.sh"
    If the file is missing, that means this particular example hasn’t been installed. I’ll use section 6B of the full guide to create it; an existing player may have another refresh method.
  3. For an existing example file, I’ll pause automation and open it:
    touch "$HOME/warehouse-maintenance"
nano "$HOME/bin/warehouse-refresh.sh"
    I’ll set REFRESH_SECONDS=300. In nano, I’ll save with Ctrl+O, Enter, then exit with Ctrl+X.
  4. For a first-time test only, with no other copy of the helper running, I’ll make it executable, remove the pause file, and start it from the Pi desktop terminal:
    chmod +x "$HOME/bin/warehouse-refresh.sh"
rm -f "$HOME/warehouse-maintenance"
"$HOME/bin/warehouse-refresh.sh"
    The terminal stays busy because the helper keeps running. I’ll click the report browser so it has focus, then watch for a reload after five minutes. To stop this test, I’ll return to the terminal and press Ctrl+C.
  5. I’ll add the helper to $HOME/.config/labwc/autostart with IT, following section 6C. If it’s already listed, I won’t add a duplicate. That makes the Pi start it automatically after desktop login.
  6. If a helper is already running and I’m changing its timing, I’ll save the file, remove the pause file, and use the approved reboot procedure. The old process won’t pick up a changed interval just because I saved the file.
  7. After reboot, I’ll confirm the report opens and reloads on its own. I won’t need a keyboard or an open terminal for normal daily operation.

I’ll start with one report so I can verify reloads before adding rotation. The two-tab example in section 7 replaces this helper; I won’t run both versions together.

If I only have a sealed box and no login: my next step is the access demonstration with IT. I can own the refresh logic, but I can’t configure a device I haven’t been given access to.

Setting up my refresh mechanism for Direct Lake

Our reports use Direct Lake. I’ll check three stages separately: data ingestion into OneLake, the semantic model seeing the updated data, and the TV report querying the model again. The Direct Lake setup section covers the settings and test.

Display refresh

  1. I’ll start with browser/player reloads. I can test native fixed-interval page refresh for our Direct Lake reports with the capacity administrator; I won’t assume DirectQuery-specific authoring steps apply.
  2. For the single-report script, I’ll set REFRESH_SECONDS=300 for a five-minute reload.
  3. For the two-report script, I’ll set DWELL_SECONDS=60. That example reloads each report on its next turn, roughly every two minutes with two tabs. Independent five-minute reloads need a player or a different scheduler.
  4. I’ll coordinate the startup entry with IT, pause automation before edits, and restart the helper after saving. Editing a running script alone doesn’t apply the new timing.
  5. I’ll check that reloads keep the browser full screen and return to the right report page and filters.

My Fabric / Direct Lake checks

  1. I’ll confirm the ingestion jobs deliver the expected records to OneLake.
  2. I’ll review the Direct Lake model settings and batch-update approach using the full setup guide.
  3. I’ll check the model returns a known new record before testing the TV refresh.
  4. I’ll add an accurate ingestion/data-as-of timestamp with a clear time zone.
  5. I’ll test the whole path, including the next browser reload, and record the actual delay.
A five-minute browser reload doesn’t guarantee five-minute-old data. I’ll document the actual source-update and model-refresh timing for each report.

My daily check

Changing a report or its timing

  1. I’ll check the new report and intended view on my work computer.
  2. I’ll confirm the display identity can open it.
  3. I’ll update the player or Pi configuration with the link, order, and timing. If that setting is locked down, I’ll ask IT to apply the change or provide access.
  4. I’ll verify the result on the TV after a reload and restart.

Maintenance controls for the example scripts

These steps apply if we use the scripts in the full setup guide. A managed player may have different controls.

  1. I’ll pause automatic keys and browser relaunch:
    touch "$HOME/warehouse-maintenance"
  2. I’ll close Chromium with Alt+F4. If I need to sign in again, I’ll open the same profile normally:
    chromium --user-data-dir="$HOME/.config/warehouse-chromium" \
  'https://app.powerbi.com'
  3. After signing in with the approved identity, I’ll close that normal browser window.
  4. I’ll remove the pause file so the running launcher returns to kiosk mode:
    rm -f "$HOME/warehouse-maintenance"

The pause file survives a restart. If the Pi opens to the desktop after maintenance, I’ll check whether I left it in place. After changing a script, I’ll use the agreed restart procedure so the updated version runs.
