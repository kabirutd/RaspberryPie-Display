Reports and daily use

My part after IT setup

I’ll manage the reports, refresh, and rotation once the Pi and TV are ready.

OverviewIT setup requestFull setup guideMy part after setup

I develop the reports, so I’ll own the report pages, data-refresh settings, display refresh mechanism, and rotation. IT will handle the Pi, TV, network, startup, and any administrator-only settings.

Before I take over

  1. I’ll provide the exact report links and the pages and filters I want on the TV.
  2. I’ll grant the agreed display identity access where I have permission and ask an administrator for anything else.
  3. I’ll get access to the player settings or Pi scripts, plus the startup and recovery instructions.
  4. I’ll test my refresh configuration with IT and keep the support contacts and known sign-in limits in the handoff notes.

I’ll confirm which account is approved for the shared screen rather than treating my own work account as the default.

Setting up my refresh mechanism

I’ll treat display reloads and source-data updates as two separate jobs.

Display refresh

  1. I’ll use native Power BI automatic page refresh if the connection type and capacity support the timing I need. Otherwise, I’ll set a browser/player reload interval.
  2. For the single-report script, I’ll set REFRESH_SECONDS=300 for a five-minute reload.
  3. For the two-report script, I’ll set DWELL_SECONDS=60. That example reloads each report on its next turn, roughly every two minutes with two tabs. Independent five-minute reloads need a player or a different scheduler.
  4. I’ll coordinate the startup entry with IT, pause automation before edits, and restart the helper after saving. Editing a running script alone doesn’t apply the new timing.
  5. I’ll check that reloads keep the browser full screen and return to the right report page and filters.

Power BI data refresh

  1. I’ll check whether each report uses Import, DirectQuery, or another connection mode.
  2. For Import models, I’ll configure the semantic-model refresh schedule, verify credentials/gateway access, and check Refresh history.
  3. For automatic page refresh, I’ll configure each page and confirm the effective interval after publishing.
  4. I’ll add a “data as of” timestamp tied to the actual source or model refresh, with a clear time zone.
  5. I’ll test a known source-data change from start to finish. If the required timing needs capacity or infrastructure changes, I’ll work with IT and the Power BI administrator.
A five-minute browser reload doesn’t guarantee five-minute-old data. I’ll document the actual source-update and model-refresh timing for each report.

My daily check

Changing a report or its timing

  1. I’ll check the new report and intended view on my work computer.
  2. I’ll confirm the display identity can open it.
  3. I’ll update the player or Pi configuration with the link, order, and timing. If that setting is locked down, I’ll ask IT to apply the change or provide access.
  4. I’ll verify the result on the TV after a reload and restart.

I’ll use the safe restart procedure rather than routinely unplugging the Pi. A restart won’t repair report permissions or a failed source refresh.

Maintenance controls for the example scripts

These steps apply if we use the scripts in the full setup guide. A managed player may have different controls.

  1. I’ll pause automatic keys and browser relaunch:
    touch "$HOME/warehouse-maintenance"
  2. I’ll close Chromium with Alt+F4. If I need to sign in again, I’ll open the same profile normally:
    chromium --user-data-dir="$HOME/.config/warehouse-chromium" \
  'https://app.powerbi.com'
  3. After signing in with the approved identity, I’ll close that normal browser window.
  4. I’ll remove the pause file so the running launcher returns to kiosk mode:
    rm -f "$HOME/warehouse-maintenance"

The pause file survives a restart. If the Pi opens to the desktop after maintenance, I’ll check whether I left it in place. After changing a script, I’ll use the agreed restart procedure so the updated version runs.
